# Локальный запуск

Для тестовой сборки образов используйте пример окружения напрямую. Поля для ключа RunPod и сервисных токенов в примере оставлены пустыми.

```sh
docker compose --env-file infra/.env.example build
```

При первом локальном запуске скопируйте `infra/.env.example` в `.env` в корне репозитория и задайте отдельные пароли PostgreSQL и Grafana. Для существующего стенда добавьте `GRAFANA_ADMIN_PASSWORD` в текущий `.env`. Корневой `.env` исключён из Git. Проверьте конфигурацию и запустите сборку из корня проекта.

```sh
docker compose config --quiet
docker compose up -d --build
docker compose ps
curl --fail http://localhost:8080/health/live
```

Корневой Compose собирает цели `backend`, `ml-service` и `caddy` из общего [Dockerfile](../Dockerfile) и запускает PostgreSQL из образа `postgres:17`. Образ Caddy собирает фронтенд из зафиксированных зависимостей и раздаёт его по адресу `http://localhost:8080`. Flyway применяет схему при старте Java. `/health/ready` показывает `200` после появления активного снимка каталога.

Для запуска панели Runpod в том же стеке настройте `runpod-panel/.env` и добавьте `COMPOSE_PROFILES=runpod-panel` в корневой `.env`. После этого `docker compose up -d --build` поднимает весь стенд, а `docker compose down` завершает все его контейнеры с сохранением томов. [Настройка панели и перенос её состояния](../runpod-panel/README.md).

Для проверки RunPod на синтетических данных заполните `RUNPOD_API_KEY`, `RUNPOD_ENDPOINT_ID`, имя модели на endpoint в `RUNPOD_MODEL` и метку её версии в `RUNPOD_MODEL_VERSION`. Задайте отдельный токен внутреннего HTTP API в `ML_SERVICE_TOKEN`. Проверочные запросы к FastAPI описаны в инструкции ML-сервиса. [Настройки FastAPI](../ml-service/README.md)

Для полного модельного сценария нужны активный каталог и подключение Spring Boot к FastAPI. В подтверждённом российском контуре задайте `ML_BASE_URL=http://ml-service:8000` и `ML_DATA_REGION=RU`. Оба сервиса получают один `ML_SERVICE_TOKEN` из корневого `.env`. Для импорта каталога укажите `CATALOG_FEED_URL` либо смонтируйте файл в контейнер backend и укажите путь через `CATALOG_FEED_FILE`. [Архитектура](../ARCHITECTURE.md) · [Настройки бэкенда](../backend/README.md)

Конфигурация по умолчанию слушает loopback. Если локально используются оба адреса, задайте `CHAT_PUBLIC_ORIGIN=http://localhost:8080,http://127.0.0.1:8080`, подставив порт стенда. Для публичного стенда задайте домен в `SITE_ADDRESS`, адрес привязки VPS в `EDGE_BIND`, порты 80 и 443 и точный HTTPS-origin в `CHAT_PUBLIC_ORIGIN`.

## Мониторинг расхода токенов

Основной Compose запускает Prometheus, Grafana, Loki и Grafana Alloy вместе с приложением. Prometheus каждые 15 секунд читает `ml-service:8000/metrics` и `backend:8081/actuator/prometheus` по сети Compose. Alloy читает JSON-журнал вызовов RunPod из общего тома ML-сервиса и отправляет строки в Loki. Prometheus и Loki хранят историю 30 дней в именованных томах. Том Alloy хранит позицию чтения, том Grafana — настройки и пользователей. При обычном перезапуске контейнеров тома сохраняются.

Откройте Grafana на [127.0.0.1:3000](http://127.0.0.1:3000) или на порту из `GRAFANA_PORT`. Для стенда на VPS с доступом по SSH откройте туннель и используйте тот же локальный адрес. Замените правый порт в команде, если на VPS настроен другой `GRAFANA_PORT`.

```sh
ssh -N -L 127.0.0.1:3000:127.0.0.1:3000 user@vps
```

При первом запуске имена и пароль администратора берутся из `GRAFANA_ADMIN_USER` и `GRAFANA_ADMIN_PASSWORD`. Для команды создайте именные аккаунты с ролью Viewer в Grafana. Вход обязателен, саморегистрация отключена. При повторном запуске пароль берётся из существующей базы Grafana, его можно изменить через интерфейс администратора. Caddy обслуживает публичный чат, Grafana привязана к loopback.

Откройте панель **Расход токенов RunPod**. Выбранный диапазон применяется к счётчикам и поиску в Loki.

- Вход и выход соответствуют `prompt_tokens` и `completion_tokens`, разбивка показывает `interpret` и `compose`.
- Среднее на вызов использует только вызовы с полученной статистикой. Среднее на реплику делит измеренные токены на все новые сохранённые пользовательские сообщения, включая сообщения, обработанные без модели. Повтор сохранённого хода и повторная попытка с `retry_of_turn_id` используют исходное сообщение.
- Доля вызовов с usage показывает полноту измерения. Пустое значение среднего или доли означает, что для расчёта нет знаменателя или данных за период. Prometheus рассчитывает прирост по снимкам счётчиков и экстраполирует к границам выбранного диапазона, поэтому итог за короткий период может отличаться от суммы отдельных записей. [Функция increase](https://prometheus.io/docs/prometheus/latest/querying/functions/#increase)
- Для поиска возьмите `request_id` из SSE-события `accepted`, вставьте его в поле панели и выберите время вызова. При рекомендации строки `interpret` и `compose` имеют общий ID. `usage_status=missing` означает, что оба поля токенов пусты. `status=error` допускает `usage_status=reported`, если RunPod вернул статистику для ответа, который ML-сервис отклонил.

Для проверки конфигурации и сквозного прогона используйте отдельный тестовый стенд с синтетическим каталогом, тестовым профилем RunPod и пустой БД.

```sh
docker compose config --quiet
docker compose exec prometheus promtool check config /etc/prometheus/prometheus.yml
docker compose exec alloy alloy validate /etc/alloy/config.alloy
docker compose ps
```

Отправьте сообщение, дающее рекомендацию, и сообщение, дающее уточнение. Сверьте найденные строки с `usage` в JSON и финальном SSE-событии провайдера. После пары интервалов сбора проверьте агрегаты панели. Выполните `docker compose restart ml-service` и повторите запросы к панели за тот же период, включая поиск по прежнему `request_id`.
