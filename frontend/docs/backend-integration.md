# Передача Frontend разработчику Backend

Актуально: 26 ноября 2026. Основная спецификация — `../../ARCHITECTURE.md`,
формат — `../../contracts/public.openapi.yaml`, примеры — `../../contracts/examples/`.
Контракты, Backend и ML в этой работе не изменялись. Готовность клиентского кода
к подключению проверена с контрактными моками и перехваченным API; это не результат
испытания настоящего Spring Boot/ML, прикладные маршруты которого ещё нужно реализовать.

## Что можно подключать без изменения Frontend-контракта

| Возможность | Метод / данные | Реализация UI |
| --- | --- | --- |
| Создание сессии | POST `/api/v1/sessions`, 201 `{session_id}` и cookie | Новый диалог, восстановление сохранённого UUID |
| История и восстановление | GET `/api/v1/sessions/{id}` → Session | Сохранённый/частичный ответ, выбранная позиция, состояние хода |
| Отправка и генерация | POST `/api/v1/sessions/{id}/messages`, JSON + SSE | Оптимистичная реплика, статусы, текстовые блоки, итог, ошибки |
| Выбор предложения | POST `/api/v1/sessions/{id}/selection` | `offer_id` + `catalog_version`, проверка через GET, OFFER_CHANGED |
| Карточки и источники | OfferCard / Source из GET и done | Цена-строка, отсутствие цены, статус снимка, параметры, безопасные HTTPS-ссылки |
| Черновик КП (опционально) | POST `/api/v1/sessions/{id}/quote-drafts` → PDF | Только при quotes_enabled=true и выбранной позиции; проверка MIME/сигнатуры; без расчётов в браузере |

Cookie — серверная `softline_session`, HttpOnly/Secure/SameSite=Lax. JS не читает токен.
UUID текущего диалога хранится в localStorage, незавершённый запрос и подтверждённые
идентификаторы — в sessionStorage текущей вкладки. API- и mock-пространства разделены.
Доступ к чужой/отсутствующей сессии ожидается как 404. POST проверяет Origin на сервере.
Прямых обращений к ML или облачных ключей в браузере нет.

## Запуск для совместной разработки

Из `frontend/`, Node.js совместимый с package.json (проверен 24.22.3), pnpm 11.25.0:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Frontend: `http://127.0.0.1:5173`. `/api` и `/health` проксируются на
`http://127.0.0.1:8080`. Для другого адреса:

```sh
BACKEND_PROXY_TARGET=http://127.0.0.1:8090 pnpm dev
```

В `pnpm dev` MSW не запускается. Для интеграции используйте отдельный чистый контекст
браузера; не переносите mock-сессию в API-режим. При использовании старой вкладки
dev:mock проверьте отключение её service worker перед проверкой реального сервера.
В proxy не задан changeOrigin: Backend должен допускать фактический Origin фронтенда
в согласованном dev-режиме. Cookie, особенно Secure на локальном HTTP, нужно проверить
в выбранном браузере совместно с Backend. На стенде используется один HTTPS origin.

```sh
pnpm check
pnpm test:e2e
pnpm build
pnpm preview
```

`preview` слушает 127.0.0.1:4173 и **не имеет dev-proxy**. Для настоящей интеграции
production-статику и API нужно обслуживать одним origin через инфраструктуру команды.
`dist/` и worker dev:mock не публикуются Git-коммитом; dist создаётся сборкой. В production
нет MSW-обработчиков/worker; синтетические примеры менеджерского UI могут оставаться в JS-бандле как
несекретные fixtures, но production-интерфейс не подставляет их вместо серверной очереди.

## SSE: обязательные гарантии

1. POST с `client_message_id`, `text`, при явном повторе `retry_of_turn_id`.
   Один активный ход. ID одного запроса не должен создавать две пользовательские реплики.
2. Ответ 200 `text/event-stream`, JSON в data; события заканчиваются пустой строкой.
   Первое событие — accepted с turn/client/user/request ID. Далее status/delta,
   затем ровно один done или failed с тем же turn_id. Heartbeat-комментарии допустимы.
3. `delta.seq` начинается с 1, растёт без пропусков. Дубликаты UI отбрасывает;
   пропуск, битый JSON или закрытие без терминального события запускают GET-восстановление.
4. done содержит окончательный сохранённый Message с cards/sources. GET после done
   уже должен показывать этот результат и завершённый ход. БД — источник истины.
5. Ошибка до потока — контрактный JSON с code/message/request_id. После открытия —
   failed с retryable. Повтор ошибки — новый client_message_id, прежний text и retry_of_turn_id.
6. GET для running ограниченно опрашивается (16 проверок, интервал 1–5 с).
   SSE/скачивание PDF ожидают до 120 с, JSON-запросы — до 15 с.
   Клиент не объявляет серверный ход завершённым по собственному таймеру.

Используется POST/fetch, не EventSource; Last-Event-ID и возобновление по курсору
не реализуются текущим контрактом. UI-прокрутка, размеры пузырей, переход между разделами
и черновик ввода не меняют содержание запроса или обработку событий.

## Что пока является только демонстрацией

- Ответы каталога/знаний в `pnpm dev:mock` — синтетические примеры SSE. Это не работа ML.
- Очередь менеджера, статусы, размеченные требования и регистрация DEMO-обращения —
  изолированная локальная модель. Снимок включает точную переписку, товары и источники.
  Реальному сотруднику ничего не отправляется. Это явно обозначено в UI.
- В API/production-режиме менеджерская очередь показывает отсутствие подключения;
  клиенту не сообщается об успешной передаче. Публичный GET сессии не используется
  как менеджерский доступ ко всем обращениям.
- PDF в mock-режиме — статический маркированный файл без коммерческой силы,
  не содержит расчёта по выбранной позиции. Настоящий PDF должен создать Backend.
- Счёт, оплата, загрузка документов, CRM и ответы менеджера из UI не реализованы.

## Что необходимо Backend

1. Реализовать публичные маршруты выше, сессионную cookie, Origin, сохранение истории,
   идемпотентность, ошибки/лимиты и восстановление. Health в каркасе не заменяет эти методы.
2. Подключить каталог/знания/ML по командной архитектуре; отдавать проверенные факты,
   цены, наличие и версии. Null/0 не должны превращаться в бесплатную цену.
3. Для реальной передачи согласовать расширение контракта: регистрация, стабильный ID,
   причина/время/статус, снимок требований и истории, идемпотентность и ошибки.
   Для очереди — серверное чтение и отдельная менеджерская авторизация/область доступа.
4. Структурированные requirements есть во внутреннем ML API, но отсутствуют в публичной
   Session. Frontend их не извлекает сам и не обращается к внутреннему interpret.
5. Для документов — включение флага, актуальность выбранной цены/наличия/версии,
   реквизиты заказчика и подтверждённые условия. Счёт требует отдельного согласованного API.

Нерешённые детали GET-повтора, seq, attributes, лимитов и cookie — в
`backend-questions.md`. Эти вопросы не скрыты под вымышленными endpoint-ами.

## Совместный приёмочный прогон на настоящем API

- Новый диалог → известный продукт → уточнения → рекомендации → выбор → reload.
- Подбор по потребности; вопрос по знаниям с источниками и временем снимка.
- Отсутствующая/нулевая цена, неизвестные параметры, OFFER_CHANGED.
- 400/403/404/409/429, failed retryable, повтор без дублирования вопроса.
- Обрыв SSE, reload во время генерации, running/partial → конечное сохранённое состояние.
- Переход к менеджеру и обратно во время потока: исходный POST не отменяется.
- PDF при включённом флаге; disabled/нет выбора/изменившаяся позиция/ошибка документа.
- HTTPS, cookie/Origin, Caddy без задержки буферизации SSE, холодный запрос модели,
  desktop/mobile, длинный ввод и чтение истории во время генерации.

До этого прогона корректно говорить «Frontend готов к интеграции», а не «реальная
интеграция Backend/ML завершена».
