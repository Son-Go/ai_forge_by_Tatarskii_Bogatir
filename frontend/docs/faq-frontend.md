# FAQ: раздел №1 «Фронт»

Реализовано по разделу №1 предоставленного `faq-manager-review-plan.md` и уточнению пользователя от 27.11.2026. Ветка `feat/frontend-faq-review` основана на `main` (`1dda4cf`). Java, ML, КП и счёт в эту задачу не входят.

## Что готово

- `src/features/faq/FaqReviewPanel.tsx` — компактная панель «Ответ для FAQ», использующая существующие дизайн-токены и `SourcesList` в обеих темах.
- Пять **отображаемых** состояний из задания: «В очереди», «В FAQ», «Нужна проверка», «Ответ по заказу», «Отклонено». Это подписи интерфейса, не предполагаемые значения серверного enum.
- В ручной проверке доступны изменение вопроса и ответа, причина сомнений, просмотр и подтверждение предоставленного источника, публикация и отклонение. В опубликованном состоянии — чтение вопроса/ответа/источника и снятие с публикации.
- Публикация требует непустых вопроса и ответа и подтверждённого безопасного источника. Редактирование текста или обновление идентификатора, URL, названия либо дат источника снимает подтверждение. Отсутствующий источник нельзя выдумать или подменить вводом URL.
- Асинхронные действия защищены от повторного нажатия; поля блокируются на время запроса. При ошибке текст остаётся в форме, повтор выполняется только явно. При размонтировании передаётся сигнал отмены. Успешный Promise сам по себе не меняет статус: его и опубликованный текст должен передать родитель из проверенного ответа сервера.
- `ManagerConnected.tsx` добавляет панель только в доступную через существующий авторизованный GET карточку со статусом `resolved`. У активных обращений панели нет. Без FAQ-данных отображается «Данные проверки FAQ пока недоступны», без вымышленного кандидата и действий.
- Клиентский FAQ-ответ уже совместим с обычными `Message`/`Source`: ответ ассистента и источник вида `knowledge` отображаются существующими компонентами как при SSE `done`, так и из восстановленной истории. Новый вид сообщения, флаг FAQ и отдельный клиентский endpoint не вводились.

## Где проходит граница интеграции

В актуальных `contracts/manager.openapi.yaml` и его frontend-снимке пока **нет** чтения FAQ-кандидата, публикации, отклонения и снятия с публикации. Поэтому `handoffApi.ts`, контракты, generated types и HTTP-транспорт не менялись. Реальные действия FAQ сейчас не подключены; готовность UI не означает готовность сквозного серверного сценария.

`FaqReviewPanelProps` содержит только данные представления и асинхронные обработчики `onPublish(question, answer, source, signal)`, `onReject(signal)`, `onUnpublish(signal)`. Это не JSON-запросы. Адаптер после получения OpenAPI должен:

1. Читать кандидата с текущей авторизацией кабинета только при подтверждённом доступе к закрытому обращению; передавать `loading`/`error`.
2. Проверять ответы через согласованные схемы, явно сопоставлять серверные состояния отображаемым подписям. Не определять FAQ-статус из `handoff.status`.
3. Передавать обработчики только для подтверждённых доступных действий. Формировать тела запросов и идентификаторы источников строго по OpenAPI.
4. Дождаться актуального результата сервера и обновить props, затем завершить обработчик. При ошибке отклонить Promise с безопасным для пользователя сообщением. Не делать оптимистических переходов.
5. Не размонтировать редактор при фоновом обновлении/ошибке: `loading` с текущими данными сохраняет черновик. При смене обращения использовать отдельный ключ, как сейчас в `ManagerConnected.tsx`. Черновики намеренно не сохраняются в localStorage.

Нужно получить от Backend: маршруты/методы и DTO чтения и действий, точный enum состояний, правила доступности действий и доступа к источникам, ограничения полей, представление отсутствующего кандидата, ошибки, правила повторного запроса/конкурентного редактирования и способ обновления результата фоновой проверки. До этого HTTP-адаптер не реализуется. Сбор кандидата, проверка ML, публикация, поиск FAQ и сохранение ответа с источником в историю остаются ответственностью других разделов исходного задания.

## Изолированная проверка интерфейса

Запустить существующий `pnpm dev` из `frontend/`, затем открыть `http://127.0.0.1:5173/tests/fixtures/faq-review.html` (при занятом порте использовать адрес Vite).

Эта тестовая страница явно помечена как синтетическая, не добавлена в навигацию приложения и не входит в production-сборку. Она передаёт props и имитирует только асинхронные callbacks в памяти; FAQ URL/JSON/серверных статусов и сетевых запросов нет. Здесь можно выбрать все пять состояний, обе темы и ошибку следующего действия. Это не демонстрация работы Backend.

## Проверки

- `pnpm check` — соответствие существующим контрактам, TypeScript, ESLint, модульные тесты, production build.
- `pnpm test:api-browser` — существующие API-сценарии и новые проверки: редактор/подтверждение/ошибка/повтор/снятие с публикации без FAQ HTTP, панель только в доступном закрытом обращении, обычный ответ с источником через SSE и после reload. Desktop/mobile, две темы; панель проверяется также при ширине 320 px и reduced motion.
- `pnpm test:e2e` — регрессия существующего демонстрационного приложения.

Тестовые данные синтетические. Прогон с подменой существующего API не подтверждает работу живого Java/ML; сквозная приёмка возможна после публикации FAQ-контрактов и реализации остальных разделов плана.
